## 2. Newly Found Issues This Round

### 2.1 [Critical] Template code generated by CLI `new` does not compile

- **File**: `ecat-cli/src/main.rs:79-97`
- **Problem**: the generated `Cargo.toml` uses `workspace = true` dependency references and `path = "../ecat"` relative paths, but the standalone project created by `ecat new myapp` is not inside the e-cat workspace — all of these references fail to resolve
- **Impact**: projects created by `ecat new` cannot compile at all
- **Fix**: the template should use versioned real dependencies instead of workspace references

```toml
# 当前（错误）：
tokio.workspace = true           # 项目不在 workspace 中，报错
ecat = { path = "../ecat" }      # 相对路径无效

# 应改为：
tokio = { version = "1", features = ["full"] }
ecat = "1.0.5"
```

### 2.2 [Critical] ecat-data-sqlx `transaction()` discards the real database transaction handle

- **File**: `ecat-data-sqlx/src/lib.rs:100-106`
- **Problem**: `pool.begin()` returns a real database transaction handle `Transaction<'_, DB>`, but the code binds it as `_tx` and drops it immediately. When `_tx` is dropped, the database transaction rolls back automatically. The returned `ecat_data::Transaction` is a shell whose `commit()/rollback()` methods have no effect
- **Impact**: all code using `transaction()` runs without transaction protection; data consistency cannot be guaranteed
- **Fix**: `ecat_data::Transaction` needs to be redesigned to hold the real database transaction handle

### 2.3 [Medium] SecurityLayer does not scan the request body

- **File**: `ecat-security/src/lib.rs:117-127`
- **Problem**: `call()` only scans the URI and HTTP headers, completely ignoring the request body. Attackers can easily bypass detection by placing SQL injection/XSS payloads in the POST body
- **Impact**: significantly reduces the effective coverage of attack detection
- **Fix**: add body scanning capability, or provide a public `scan_body()` method for callers to use after reading the body

### 2.4 [Medium] RateLimitLayer uses a synchronous Mutex and no expiry cleanup

- **File**: `ecat-middleware/src/ratelimit.rs:10-38`
- **Problem 1**: `std::sync::Mutex` used in async context — if the lock is contended, it blocks the whole tokio worker thread
- **Problem 2**: `buckets: HashMap<String, (u32, Instant)>` never cleans up expired keys; long-running servers grow memory without bound (each new IP/key occupies memory forever)
- **Impact**: performance degradation under high concurrency, memory leak after long uptime
- **Fix**: switch to `tokio::sync::Mutex` and periodically clean expired entries in `allow()`

### 2.5 [Medium] ecat-data-sqlx has no parameterized API for raw SQL

- **Files**: `ecat-data-sqlx/src/lib.rs:24-29, 32-36`
- **Problem**: `execute(&self, sql: &str)` and `query(&self, sql: &str)` only accept raw SQL strings; the trait layer has no parameter binding methods. Callers who concatenate user input into SQL will introduce SQL injection
- **Impact**: although the trait itself does not directly expose a vulnerability, the lack of a parameterized API tempts callers into writing unsafe code
- **Suggestion**: add `execute_with` and `query_with` methods to the `RdbmsClient` trait using parameter binding

### 2.6 [Low] Arc::clone in query() is still inside the closure

- **File**: `ecat-data-sqlx/src/lib.rs:50-53`
- **Problem**: `let cols = std::sync::Arc::clone(&columns)` executes inside the `rows.iter().map()` closure. Although Arc::clone is lightweight (just an atomic reference count increment), it can be hoisted outside the closure to avoid one atomic operation per row
- **Suggestion**: clone once before `iter()` and capture that clone in the closure

### 2.7 [Low] ProtoCodec's trait impl is inconsistent with the new API

- **File**: `ecat-encoding/src/proto.rs`
- **Problem**: the `Codec` trait's `encode/decode` still only return errors; the new `encode_message/decode_message` are the correct path but their names do not match the trait. Users may first try `codec.encode()` and then wonder why it fails
- **Suggestion**: state in the docs/comments that proto types should use `encode_message/decode_message` rather than the Codec trait methods
