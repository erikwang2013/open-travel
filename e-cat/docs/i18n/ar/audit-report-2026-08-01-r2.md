## 2. المشكلات المكتشفة حديثًا في هذه الجولة

### 2.1 [خطير] كود القالب الذي يولده CLI `new` لا يُترجم

- **الملف**: `ecat-cli/src/main.rs:79-97`
- **المشكلة**: يستخدم ملف `Cargo.toml` المُولَّد مراجع تبعيات `workspace = true` ومسارًا نسبيًا `path = "../ecat"`، لكن المشروع المستقل الذي ينشئه `ecat new myapp` ليس داخل workspace الخاص بـ e-cat، وكل هذه المراجع ستفشل في التحليل
- **التأثير**: المشروع الذي ينشئه `ecat new` لا يمكن ترجمته أصلًا
- **الإصلاح**: يجب أن يستخدم القالب تبعيات فعلية برقم إصدار بدلًا من مراجع workspace

```toml
# الحالي (خطأ):
tokio.workspace = true           # المشروع ليس في workspace، خطأ
ecat = { path = "../ecat" }      # المسار النسبي غير صالح

# يجب أن يكون:
tokio = { version = "1", features = ["full"] }
ecat = "1.0.5"
```

### 2.2 [خطير] `transaction()` في ecat-data-sqlx تتجاهل مقبض المعاملة الحقيقي لقاعدة البيانات

- **الملف**: `ecat-data-sqlx/src/lib.rs:100-106`
- **المشكلة**: يُرجع `pool.begin()` مقبض المعاملة الحقيقي `Transaction<'_, DB>`، لكن الكود يربطه باسم `_tx` ثم يتجاهله فورًا. عند إسقاط `_tx`، تُتراجع معاملة قاعدة البيانات تلقائيًا. إن `ecat_data::Transaction` المُرجعة قشرة فارغة، وطريقتا `commit()/rollback()` بلا أي تأثير
- **التأثير**: كل الكود الذي يستخدم `transaction()` يعمل دون حماية معاملات، ولا يمكن ضمان اتساق البيانات
- **الإصلاح**: إعادة تصميم بنية `ecat_data::Transaction` لتحمل مقبض المعاملة الحقيقي لقاعدة البيانات

### 2.3 [متوسطة] SecurityLayer لا يفحص جسم الطلب

- **الملف**: `ecat-security/src/lib.rs:117-127`
- **المشكلة**: يفحص `call()` URI ورؤوس HTTP فقط، ولا يتحقق من جسم الطلب إطلاقًا. يمكن للمهاجم وضع حمولة حقن SQL/XSS في جسم POST وتجاوز الكشف بسهولة
- **التأثير**: تقليل كبير في التغطية الفعلية لكشف الهجمات
- **الإصلاح**: إضافة قدرة فحص الجسم، أو توفير طريقة عامة `scan_body()` ليستخدمها المستدعي بعد قراءة الجسم

### 2.4 [متوسطة] RateLimitLayer يستخدم Mutex متزامن + دون تنظيف انتهاء الصلاحية

- **الملف**: `ecat-middleware/src/ratelimit.rs:10-38`
- **المشكلة 1**: `std::sync::Mutex` مستخدم في سياقات غير متزامنة — عند تنافس على القفل، سيحجب خيط عمل tokio بأكمله
- **المشكلة 2**: `buckets: HashMap<String, (u32, Instant)>` لا تنظف المفاتيح المنتهية أبدًا، فينمو استخدام ذاكرة الخادم طويل المدى بلا حدود (كل IP/مفتاح جديد يحتل الذاكرة إلى الأبد)
- **التأثير**: تدهور الأداء تحت التزامن العالي، وتسريب ذاكرة بعد التشغيل الطويل
- **الإصلاح**: التحول إلى `tokio::sync::Mutex`، والتنظيف الدوري للإدخالات المنتهية في `allow()`

### 2.5 [متوسطة] لا واجهة SQL مجردة مع معاملات في ecat-data-sqlx

- **الملف**: `ecat-data-sqlx/src/lib.rs:24-29, 32-36`
- **المشكلة**: يقبل كل من `execute(&self, sql: &str)` و`query(&self, sql: &str)` سلاسل SQL خام فقط، ولا توجد طريقة ربط معاملات على مستوى trait. إذا ضمّن المستدعي مدخلات المستخدم في SQL، سيؤدي ذلك إلى حقن SQL
- **التأثير**: رغم أن trait نفسه لا يعرض ثغرة أمنية مباشرة، فإن غياب واجهة المعاملات يغري المستدعيين بكتابة كود غير آمن
- **الاقتراح**: إضافة طريقتي `execute_with` و`query_with` إلى trait `RdbmsClient` لاستخدام ربط المعاملات

### 2.6 [منخفضة] Arc::clone في query() ما زالت داخل الإغلاق

- **الملف**: `ecat-data-sqlx/src/lib.rs:50-53`
- **المشكلة**: يُنفَّذ `let cols = std::sync::Arc::clone(&columns)` داخل إغلاق `rows.iter().map()`. رغم أن Arc::clone خفيفة جدًا (مجرد زيادة عدد مرجعي ذري)، يمكن نقلها خارج الإغلاق لتجنب عملية ذرية لكل صف
- **الاقتراح**: تنفيذ clone واحدة قبل `iter()` والتقاطها في الإغلاق

### 2.7 [منخفضة] عدم اتساق تنفيذ trait في ProtoCodec مع واجهات API الجديدة

- **الملف**: `ecat-encoding/src/proto.rs`
- **المشكلة**: لا يزال `encode/decode` في trait `Codec` يُرجعان خطأ فقط؛ واجهات `encode_message/decode_message` الجديدة هي المسار الصحيح لكن أسماء الطرق لا تطابق الـ trait. قد يجرب المستخدم `codec.encode()` أولًا ثم يتساءل لماذا يفشل
- **الاقتراح**: توضيح في التوثيق/التعليقات: يجب استخدام `encode_message/decode_message` للأنواع proto بدلًا من طرق trait Codec
