## Находки (15 пунктов)

### Безопасность

#### 1. [Критично] XOR-«шифрование» — не настоящее шифрование
**Файл:** `ecat-config/src/encrypted.rs:45-56`
**Проблема:** `decrypt()` использует XOR с повторяющимся ключом — это обфускация, а не шифрование; легко взламывается. Ключ повторяется на каждой позиции байта, из-за чего шифротекст крайне уязвим к частотному анализу.
**Рекомендация:** заменить на AES-256-GCM (crate `aes-gcm`) или явно пометить как «обфускацию», а не «шифрование».

#### 2. [Критично] Реализации `execute_with`/`query_with` по умолчанию молча отбрасывают параметры
**Файл:** `ecat-data/src/rdbms.rs:86-103`
**Проблема:** реализация trait по умолчанию принимает параметры, но игнорирует их (`let _ = params;`) и напрямую вызывает исходный `execute(sql)`. Все бэкенды, кроме `ecat-data-sqlx` (ClickHouse, QuestDB), наследуют это поведение. Если пользователь заменит бэкенд на параметризованный метод, параметры будут молча отброшены — уязвимость SQL-инъекции.
**Рекомендация:** реализация по умолчанию должна возвращать ошибку «не поддерживается» или каждый бэкенд должен корректно реализовывать привязку параметров.

#### 3. [Высокий] Пароли встраиваются в URL открытым текстом
**Файл:** `ecat-data-sqlx/src/lib.rs:40`, `ecat-data-redis/src/lib.rs:43`
**Проблема:** `connect_with_auth()` использует `replacen("://", "://user:pass@")`, встраивая учётные данные прямо в URL. Эти URL могут попадать в логи, сообщения об ошибках или отладочный вывод.
**Рекомендация:** использовать нативные механизмы аутентификации каждого бэкенда; или как минимум URL-кодировать имя пользователя/пароль перед встраиванием.

#### 4. [Средний] Сбой конфигурации TLS приводит к panic
**Файл:** 8 crates data-* (ClickHouse, QuestDB, Elasticsearch, OpenSearch, ArangoDB, Neo4j, NebulaGraph, InfluxDB, IoTDB)
**Паттерн:** `.expect("TLS client build failed")` — все конструкторы `from_config()` паникуют при ошибке конфигурации TLS.
**Рекомендация:** изменить `from_config()` на возврат `Result` или сделать построение TLS-клиента ленивым/отказоустойчивым.

### Корректность функциональности

#### 5. [Высокий] Header-маршрутизация `ecat-versioning` не работает
**Файл:** `ecat-versioning/src/lib.rs:56-64`
**Проблема:** `build_header_router()` вкладывает все версии в один путь `/api`, но не фильтрует по версионному header. axum регистрирует маршруты всех версий на одном пути — конфликт маршрутов и непредсказуемое поведение. Функция `extract_version()` существует, но нигде не используется в маршрутизации.
**Рекомендация:** использовать middleware/layer axum для проверки Accept-header и маршрутизации на нужный маршрут версии, а не располагать все версии на одном пути.

#### 6. [Средний] Усечение TTL в Redis: субсекундное истечение становится вечным
**Файл:** `ecat-data-redis/src/lib.rs:76-77`
**Проблема:** `Duration::as_secs()` усекает к нулю. TTL 500ms при `secs == 0` молча становится «не истекает никогда» — выполняется ветка `SET`, а не `SETEX`.
**Рекомендация:** для субсекундных TTL использовать минимум 1 секунду или `SET ... PX` (миллисекунды) вместо `SETEX`.

#### 7. [Средний] `StaticResolver::add_service` паникует при конкуренции за блокировку
**Файл:** `ecat-client/src/lib.rs:27-29`
**Проблема:** используется `try_write()` с expect — panic при наличии любого другого держателя write-блокировки. Паттерн builder делает проблему трудновоспроизводимой, но в конкурентном коде это бомба замедленного действия.
**Рекомендация:** использовать `blocking_write()` (в синхронном контексте) или принимать `&mut self`, чтобы не требовать блокировку.

### Качество кода

#### 8. [Средний] `std::sync::Mutex` в асинхронном контексте
**Файл:** `ecat-data-memcached/src/lib.rs:7,24`
**Проблема:** в async-trait реализации используется `std::sync::Mutex`. Хотя блокировка удерживается крайне коротко (только операции с HashMap), при высокой конкуренции теоретически может блокировать асинхронный runtime.
**Рекомендация:** для этого конкретного сценария in-memory кэша, где критическая секция крайне коротка и нет точек `.await`, использование `std::sync::Mutex` фактически допустимо. Но если в будущем внутри блокировки понадобится I/O, следует перейти на `tokio::sync::Mutex`.

#### 9. [Низкий] Рукописная реализация base64
**Файл:** `ecat-registry-etcd/src/lib.rs:148-193`
**Проблема:** ~45 строк рукописного кодека base64 с возможными багами на граничных случаях. В экосистеме Rust есть хорошо проверенные альтернативы, например crate `base64`.
**Рекомендация:** заменить на crate `base64`, снизив нагрузку на сопровождение и потенциальные баги.

#### 10. [Низкий] `RandomBalancer` не случаен
**Файл:** `ecat-client/src/lib.rs:91-105`
**Проблема:** в качестве источника случайности используется хэш `Instant::now()`. Одновременные вызовы в одном экземпляре получат один и тот же «случайный» выбор. `checked_add(0)` — избыточная операция.
**Рекомендация:** использовать crate `rand` или хотя бы `std::collections::hash_map::RandomState`.

#### 11. [Низкий] Лишний `Arc<Vec<String>>` в `ecat-data-sqlx`
**Файл:** `ecat-data-sqlx/src/lib.rs:79-87, 197-203`
**Проблема:** имена колонок обёрнуты в `Arc<Vec<String>>`, но каждый конструктор `Row` клонирует весь список имён (`(*cols).clone()`). `Arc` используется лишь один раз за итерацию — достаточно `Rc` или обычного `clone()`.
**Рекомендация:** в `query()` и `query_with()` заменить `Arc<Vec<String>>` на обычный `Vec<String>`. Стоимость отдельного клонирования на строку та же, что разыменование Arc + клонирование.

### Дизайн/архитектура

#### 12. [Информация] QuestDB использует GET + параметры запроса
**Файл:** `ecat-data-questdb/src/lib.rs:76, 91`
**Проблема:** SQL отправляется через GET-параметры запроса, ограниченные длиной URL (обычно ~2000-8000 символов). Большие запросы обрезаются.
**Рекомендация:** перейти на POST + body, или оставить GET для простых запросов, а для сложных использовать POST.

#### 13. [Информация] `#[allow(dead_code)]` разбросаны по коду
**Файл:** `ecat-registry-consul/src/lib.rs:225`, `ecat-data-memcached/src/lib.rs:25-28`, `ecat-auth/src/lib.rs:52`
**Проблема:** поля username/password хранятся в памяти, но помечены dead_code (в in-memory memcached не нужны; RSA-вариант в auth ещё не реализован).
**Рекомендация:** либо реализовать недостающие функциональные ветки, либо удалить эти поля, либо добавить документацию о причинах их сохранения.

#### 14. [Информация] Части HTTP-клиентов не хватает Content-Type header
**Файл:** `ecat-data-influxdb/src/lib.rs:96-103`, `ecat-data-clickhouse/src/lib.rs:87-89`
**Проблема:** часть POST-запросов не устанавливает `Content-Type` header, полагаясь на автоопределение сервером.
**Рекомендация:** всегда задавать явный Content-Type для совместимости.

#### 15. [Информация] `ecat-auth` превышает 500 строк
**Файл:** `ecat-auth/src/lib.rs` (540 строк)
**Проблема:** CLAUDE.md требует, чтобы файлы были в пределах 500 строк. auth crate — единственный файл, превышающий это ограничение.
**Рекомендация:** вынести логику проверки JWT в `ecat-auth/src/jwt.rs` или разбить по функциям.

## Заключение

Кодовая база в хорошем состоянии — компиляция, тесты и clippy полностью проходят, нет unsafe-кода и макросов panic. Две самые критичные проблемы: **XOR-«шифрование»** (фиктивная безопасность) и **реализация параметризованных запросов по умолчанию, молча отбрасывающая параметры** (уязвимость). Header-маршрутизация также полностью неработоспособна. Остальные проблемы относительно незначительны и относятся к уровню поддерживаемости.

**Рекомендуемый порядок исправления:**
1. Реализации `execute_with`/`query_with` по умолчанию → возвращать ошибку вместо молчаливого отбрасывания параметров
2. XOR-шифрование → настоящее AEAD-шифрование или переименование в «обфускацию»
3. Header-маршрутизация версий → реализовать фактическую header-маршрутизацию
4. `from_config()` → возвращать Result вместо expect-panic
5. Усечение TTL в Redis → субсекундные TTL минимум 1 секунда
