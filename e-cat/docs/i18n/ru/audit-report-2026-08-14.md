# Специализированный отчёт об аудите (безопасность и производительность) — 2026-08-14

Область аудита: workspace из 55 crates (v2.3.5). Метод: ручная проверка Cargo.lock (cargo-audit не установлен), аудит исходников путей аутентификации/TLS, проверка конкурентности и жизненного цикла ресурсов. Коммиты не выполнялись.

## Проверка CVE зависимостей

- Версии ключевых зависимостей свежие, известных неисправленных CVE нет: rustls 0.23.43, ring 0.17.14, aws-lc-rs 1.17.3, jsonwebtoken 9.3.1, tokio 1.53.1, h2 0.4.15, quinn 0.11.11, sqlx 0.8.6, zerocopy 0.8.55, time 0.3.54, openssl 0.10.81.
- hyper 0.14.32 (только от rust-s3 0.35.1, через hyper-tls 0.5) уже выше линии исправления 0.14.28.
- Примечание: в CI не установлен cargo-audit, рекомендуется добавить автоматизированную проверку в рабочий процесс.

## Находки (по убыванию серьёзности)

### S1 [Средне] Сериализация TLS-рукопожатий в HTTP → DoS медленным рукопожатием
- Место: `ecat-transport-http/src/lib.rs:134-150` (TlsListener::accept)
- Симптом: TLS-рукопожатие выполняется синхронно внутри `accept()`; axum::serve вызывает accept последовательно — одно незавершённое рукопожатие блокирует весь цикл accept.
- Влияние: атакующий, массово открывая медленные/зомби-TCP-соединения, полностью останавливает приём новых соединений (на стороне gRPC tonic спавнит рукопожатие на каждое соединение — не затронуто).
- Рекомендация: после accept — `tokio::spawn` рукопожатия с `tokio::time::timeout(10s)`, при сбое закрывать соединение.

### S2 [Средне] Неограниченный рост кэша интроспекции OAuth2 → DoS памяти
- Место: `ecat-auth/src/oauth2.rs:45,84-92`
- Симптом: `HashMap<String,(String,Instant)>` с ключом-токеном; TTL контролирует только свежесть, нет ограничения ёмкости и вытеснения.
- Влияние: поток уникальных токенов неограниченно растягивает память (каждый miss также запускает вышестоящую интроспекцию).
- Рекомендация: ограничить ёмкость (например, 10k) + регулярная очистка, или перейти на moka/LRU с вытеснением по ёмкости и TTL.

### S3 [Низко-средне] ecat-data-s3 использует устаревший rust-s3 0.35.1 (hyper 0.14 + native-tls/openssl)
- Место: `ecat-data-s3/Cargo.toml` → rust-s3 0.35.1
- Симптом: S3-клиент независимо использует стек hyper-tls/openssl; `ecat-tls::TlsClientConfig` (свой CA, клиентский сертификат, skip_verify) на S3 не действует; поверхность TLS-конфигурации неоднородна.
- Влияние: в корпоративных средах нельзя настроить приватный CA/mTLS для S3; зависимость с 2023 года медленно сопровождается.
- Рекомендация: оценить обновление rust-s3 или переход на единый клиент reqwest/rustls.

### S4 [Низко] Проверка JWT по умолчанию не включает iss/aud
- Место: `ecat-auth/src/jwt.rs:125` — `Validation::new(HS256)` только подпись+exp.
- Влияние: при общем HS256-ключе токен одного сервиса может быть принят другим сервисом (нет изоляции издателей).
- Рекомендация: в документации явно требовать конфигурацию issuer/audience в production; или добавить точку входа проверки iss по умолчанию.

### S5 [Низко] Один лишь TlsClientConfig.skip_verify делает is_enabled() истинным
- Место: `ecat-tls/src/lib.rs:23-29`
- Симптом: при одном `skip_verify: true` TLS считается «включённым», но сертификаты не проверяются — проверка молча отключается.
- Рекомендация: взаимное исключение skip_verify и ca_cert, или требовать явное двойное подтверждение.

## Производительность и ресурсы

### P1 [Низко] На пути попадания в кэш OAuth2 каждый запрос десериализует JSON
- Место: `ecat-auth/src/oauth2.rs:87` — кэш хранит сериализованную строку, при попадании всё равно `serde_json::from_str`.
- Рекомендация: кэшировать напрямую структуру `AuthClaims`, избавившись от parse на каждый запрос.

### P2 [Низко] В ecat-bench нет прогрева и оценки устойчивого состояния
- Место: `ecat-bench/src/lib.rs:run_bench` — прямой замер без warmup; холодный старт/первые аллокации пула соединений смешиваются с p99.
- Рекомендация: добавить прогревочные раунды и критерий сходимости устойчивого состояния — результаты достовернее.

### P3 [Низко] В Kafka-потребителе poll 100ms + sleep 100ms последовательно
- Место: `ecat-mq-kafka/src/lib.rs:84-92` — верхняя граница сквозной задержки сообщения ~200ms.
- Рекомендация: после poll sleep не нужен; при низкой пропускной способности можно сократить интервал poll.

## Подтверждение хороших практик

- В production-путях нет panic от unwrap/expect (в transport/auth/middleware только в тестах).
- Откат на query-параметр API key с предупреждающим логом об утечке; HashMap использует SipHash против коллизий.
- SQL-слой пробрасывает SQL вызывающего (природа фреймворка), user:pass в строке подключения корректно percent-кодируется.
- При заполненном канале потребления Kafka — блокирующее backpressure вместо отбрасывания; после drop rx задача poll корректно завершается.
- config-remote тянет с таймаутом (5s/30s); блокирующий запрос без индекса выдаёт ошибку, предотвращая busy-wait.

## Аудит корректности ядра (дополнение, взаимодополняет указанные выше безопасность/производительность)

Метод аудита: сканирование всего production-кода workspace (поиск unwrap/expect/panic, молчаливого проглатывания ошибок, асинхронной остановки, конкурентных состояний) + полная повторная проверка `cargo test --workspace` (первый прогон полностью зелёный; во время исправления S1 в transport-http были предупреждения компиляции — после завершения нужно перезапустить). Коммиты не выполнялись.

### N1 [Средне] Утечка handle после выхода задачи потребления ecat-events → события молча теряются
- Место: `ecat-events/src/lib.rs:97-101` (в цикле потребления 89-95 строк `None => break`)
- Симптом: когда mq stream возвращает None (например, закрытие broadcast channel kafka) или задача паникует, цикл потребления выходит, но JoinHandle остаётся в map `consumers`; последующий `subscribe()` того же типа события из-за `contains_key` на строке 68 (всегда истинно) не перезапускает задачу потребления → события этого типа теряются навсегда.
- Влияние: после прерывания потока удалённых событий самовосстановления нет, для восстановления нужен перезапуск процесса.
- Рекомендация: на пути выхода задачи удалять handle из map (watcher-spawn или ленивая очистка через `handle.is_finished()`).

### N2 [Средне] Ошибочная семантика group_id в subscribe ecat-mq-kafka
- Место: `ecat-mq-kafka/src/lib.rs:71-84`
- a. При group_id по умолчанию None `consumer.subscribe()` rdkafka требует group.id (librdkafka выдаёт INVALID_ARG) — при конфигурации по умолчанию подписка с высокой вероятностью сразу падает (нужна проверка на реальном железе).
- b. При заданном group_id (ecat-events подписывается по одному разу на тип события, в одной группе) Kafka делит топик по партициям между потребителями одной группы → событие определённого типа может попасть в задачу потребления другого типа и быть молча отброшено (auto.offset.reset=latest и без коммитов).
- Влияние: шина событий теряет события на бэкенде kafka.
- Рекомендация: без group_id генерировать случайный уникальный group.id; или на стороне потребителя явно назначать партиции через assign(); в документации указать, что множественные подписки должны использовать независимые группы.

### N3 [Низко] GrpcServer/WsServer не нормализуют пустой host (исправление D1 неполное)
- Место: `ecat-transport-grpc/src/lib.rs:52`, `ecat-transport-ws/src/lib.rs:58`
- Симптом: `addr.parse::<SocketAddr>()` в `GrpcServer::new(":8000")` возвращает AddrParseError (проверено на практике); `TcpListener::bind(":8000")` в WsServer резолвится в IPv6-wildcard, на машинах без IPv6 запуск падает. HttpServer уже нормализует в 0.0.0.0 — поведение трёх server API несогласовано.
- Рекомендация: единообразно нормализовать пустой host внутри new.

### N4 [Низко] TracingLayer не внедряет trace_id — расходится с заявленным в CHANGELOG 2.3.3
- Место: `ecat-tracing/src/lib.rs:72-84` (span содержит только поле service; комментарий в коде сам признаёт, что у обобщённого Req нельзя взять заголовок); `inject_trace_id()` каждый раз генерирует новый UUID, не перенося trace_id, извлечённый вышестоящим.
- Влияние: распределённая трассировка, настроенная по документации, не связывает запросы между сервисами.
- Рекомендация: отложенное связывание полей span или специализация `http::Request<B>`; inject должен переносить вышестоящий id.

### N5 [Низко] Молчаливая остановка задачи при panic в ecat-scheduler
- Место: `ecat-scheduler/src/lib.rs:53-57,83` (`let _ = handle.await` в `run()`)
- Симптом: после panic периодической задачи задача умирает без перезапуска и без логов; `run()` отбрасывает ошибку JoinHandle.
- Рекомендация: ловить panic с логом + опциональная стратегия перезапуска.

### N6 [Низко] Остаточные unwrap в production-коде (пути отравления/panic)
- `ecat-events/src/lib.rs:68,98` std `Mutex::lock().unwrap()` (при отравлении — panic); `ecat-versioning/src/lib.rs:86` unwrap у Response builder (не может не сработать, но это путь panic); `ecat-mq/src/lib.rs:110` expect уже защищён guard-ом is_none (безопасно).
- Рекомендация: в events оба места — `unwrap_or_else(|e| e.into_inner())`.

### N7 [Информация] WsServer::stop() не дожидается обновлённых WebSocket-соединений
- Место: `ecat-transport-ws/src/lib.rs:63-87`
- Соединения axum on_upgrade работают в отдельных задачах, graceful shutdown их не покрывает; long-lived-обработчики остаются после stop(), процесс завершается нечисто (семантика App::stop неполна).

### N8 [Информация] Crates с нулём тестов: ecat-data / ecat-lock / ecat-protos
- Все — trait/definition-типы; проверено, что методы по умолчанию fail-loud (возвращают ошибку, а не молчат), но контракты traits (семантика отката Transaction при drop, проверка токена блокировки) без единого юнит-теста.
- Рекомендация: добавить минимальные юнит-тесты для семантики RdbmsError/Transaction и DistributedLock.

### N9 [Информация] Параметры и вложенные поля graphql по-прежнему отбрасываются
- `ecat-graphql/src/lib.rs` execute передаёт resolver-у только `variables`; параметры полей и вложенные selection в `{ hello(name: "x") }` не передаются; в README ограничение не указано (старый отчёт L8 требовал документирования, после переписывания в 2.3.3 так и не добавлено).

### N10 [Информация] circuit-breaker учитывает только ошибки транспортного уровня
- `ecat-circuit-breaker/src/lib.rs:203-209` фиксирует как неудачу только внутренний Err; HTTP 5xx считается успехом → прерыватель цепи бесполезен при недоступности сервиса (шторм 5xx); в документации не описано.

**Статус проверки**: первый прогон `cargo test --workspace` полностью зелёный (включая doc-tests, в хвосте вывода нет ни одной неудачи); во время правок агентом S1 в transport-http были ошибки компиляции и 2 предупреждения (unused import `ensure_crypto_provider`, непрочитанный `shutdown_tx`) — промежуточное состояние, после завершения S1 нужен полный перезапуск тестов и `clippy --all-targets -D warnings`.

## Третий раунд: динамическая проверка + повторный обзор CVE + поверхности panic (специализированный, 2026-08-14)

### Повторный обзор CVE (новые находки, по серьёзности)

1. **[Средне] rustls-webpki 0.102.8 остался в дереве зависимостей** (RUSTSEC-2026-0049/0098/0099/0104: обход CRL distributionPoint, URI/wildcard name-constraints; исправленная версия 0.103.10). Основная цепочка — 0.103.13 (через rustls 0.23.43, безопасно); 0.102.8 привнесён через async-nats 0.38.0 / rumqttc 0.25.1 и покрывает цепочки TLS-клиентов NATS/MQTT. Вышестоящие не мигрировали на rustls 0.23, исправленной версии нет — контролируемый риск, рекомендуется отслеживать комментарием.
2. **[Средне-низко] rdkafka 0.36.2 со встроенным librdkafka несёт cJSON 1.7.14** (CVE-2023-53154 и серия cJSON; CVE-2025-57052 с CVSS 9.8, но затрагиваемый файл cJSON_utils.c не используется librdkafka — применимость сомнительна). Исправление наверху — librdkafka 2.10+ (PR #5346, 2026-03). ecat-mq-kafka линкуется статически — нужно сверить версию упаковки librdkafka-sys и отслеживать обновление.
3. **[Низко] rustls-pemfile 2.2.0 не сопровождается** (RUSTSEC-2025-0134) — ecat-transport-http разбирает локальные файлы при старте, это не ввод атакующего.
4. **[Низко] rsa 0.9.10** (RUSTSEC-2023-0071, тайминг-канал Marvin) — привнесён через sqlx-mysql TLS, актуален только для MySQL + RSA-обмена ключами.
5. async-nats 0.38.0 уже выше линии исправления RUSTSEC-2023-0027 (обход проверки CN) — проблем нет.

### Динамическая проверка (examples/helloworld, debug-сборка, временный порт 18080, очищено)

- /health 200, / (JSON-сериализация) 200 (27B), 404 в норме; middleware Logging корректно записывает запросы.
- **/metrics смонтирован, но возвращает 200 + пустое тело (0 байт)**: при отсутствии зарегистрированных метрик нет никакого вывода — мониторинг не может отличить «здоров/нет метрик». Рекомендуется комментарий-строка в пустом registry или 503.
- Искажённый запрос (заголовок с 0x01/0x02) → 400 Bad Request, сервис жив, последующий /health по-прежнему 200, без panic.
- Пути TLS/mTLS и middleware прерывателя цепи/лимитов: покрыты тестами ecat-transport-http/grpc и ecat-middleware (после исправления гонки mTLS всё зелёное; кейсы отклонения анонимных/ошибочных клиентских сертификатов проходят).

### Повторная проверка поверхностей panic (весь workspace, без тестовых модулей)

- Всего 31 место unwrap/expect/panic, все низкого риска: `Response::builder().body().unwrap()` (jwt/apikey/oauth2, ветки, не способные дать сбой), защита от отравления блокировок (etcd/testing), `serde_json::to_string().unwrap()` в clickhouse (теоретический panic при экстремальном NaN/inf-вводе).
- **1 место требует внимания**: `ecat-transport-http/src/tls_listener.rs:234` — при аномальном выходе фонового цикла accept внутри `accept()` срабатывает `panic!`, поток сервиса умирает (триггер жёсткий: только фатальная ошибка слушателя) — рекомендуется понизить до возврата ошибки с логом.
