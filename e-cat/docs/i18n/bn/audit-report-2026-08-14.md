## আবিষ্কার (গুরুতরতা অনুযায়ী সাজানো)

### S1 [মাঝারি] HTTP TLS হ্যান্ডশেক সিরিয়ালাইজড → ধীর হ্যান্ডশেক DoS
- অবস্থান: `ecat-transport-http/src/lib.rs:134-150` (TlsListener::accept)
- উপসর্গ: TLS হ্যান্ডশেক `accept()`-এর ভিতরে সিঙ্ক্রোনাসভাবে সম্পন্ন হয়, axum::serve accept-কে সিরিয়াল কল করে — একটি অসম্পূর্ণ হ্যান্ডশেক সংযোগ পুরো accept লুপ ব্লক করে।
- প্রভাব: আক্রমণকারী ব্যাচে ধীর/জম্বি TCP সংযোগ খুললেই সার্ভিস সম্পূর্ণ নতুন সংযোগ গ্রহণ বন্ধ করে দিতে পারে (gRPC পাশে tonic প্রতি সংযোগে হ্যান্ডশেক spawn করে, প্রভাবিত নয়)।
- পরামর্শ: accept-এর পর `tokio::spawn` দিয়ে হ্যান্ডশেক করুন এবং `tokio::time::timeout(10s)` যোগ করুন, ব্যর্থ হলে সংযোগ বন্ধ করুন।

### S2 [মাঝারি] OAuth2 ইন্ট্রোস্পেকশন ক্যাশ সীমাহীন বৃদ্ধি → মেমরি DoS
- অবস্থান: `ecat-auth/src/oauth2.rs:45,84-92`
- উপসর্গ: `HashMap<String,(String,Instant)>`-এ token কী হিসেবে, TTL শুধু ফ্রেশনেস নিয়ন্ত্রণ করে, কোনো ক্যাপাসিটি সীমা নেই, কোনো ইভিকশন নেই।
- প্রভাব: বিশাল সংখ্যক অনন্য token রিকোয়েস্টে মেমরি অসীমভাবে বৃদ্ধি পেতে পারে (প্রতি miss-এ আপস্ট্রিম introspection-ও ট্রিগার হয়)।
- পরামর্শ: ক্যাপাসিটি সীমা যোগ করুন (যেমন 10k) + নিয়মিত পরিষ্কার, অথবা ক্যাপাসিটি ও TTL ইভিকশনসহ moka/LRU ব্যবহার করুন।

### S3 [কম-মাঝারি] ecat-data-s3 পুরনো rust-s3 0.35.1 ব্যবহার করে (hyper 0.14 + native-tls/openssl)
- অবস্থান: `ecat-data-s3/Cargo.toml` → rust-s3 0.35.1
- উপসর্গ: S3 ক্লায়েন্ট আলাদা hyper-tls/openssl স্ট্যাক ব্যবহার করে, ecat-tls::TlsClientConfig (কাস্টম CA, ক্লায়েন্ট সার্টিফিকেট, skip_verify) S3-এ অকার্যকর; TLS কনফিগ পৃষ্ঠ অসামঞ্জস্যপূর্ণ।
- প্রভাব: এন্টারপ্রাইজ পরিবেশে S3 প্রাইভেট CA/mTLS কনফিগ করা যায় না; 2023-এর পর ডিপেন্ডেন্সি ধীরে রক্ষণাবেক্ষণ হয়।
- পরামর্শ: rust-s3 আপগ্রেড বা ইউনিফাইড reqwest/rustls ক্লায়েন্টে পরিবর্তনের মূল্যায়ন করুন।

### S4 [কম] JWT ডিফল্ট যাচাইয়ে iss/aud নেই
- অবস্থান: `ecat-auth/src/jwt.rs:125` — `Validation::new(HS256)` শুধু সিগনেচার+exp।
- প্রভাব: HS256 শেয়ার্ড সিক্রেটে, একটি সার্ভিসের token অন্য সার্ভিস গ্রহণ করতে পারে (কোনো ইস্যুয়ার আইসোলেশন নেই)।
- পরামর্শ: ডকুমেন্টেশনে স্পষ্টভাবে প্রোডাকশনে issuer/audience কনফিগ করা বাধ্যতামূলক করুন; অথবা ডিফল্টে iss যাচাই এন্ট্রি যোগ করুন।

### S5 [কম] TlsClientConfig.skip_verify একাই is_enabled()-কে সত্য করে
- অবস্থান: `ecat-tls/src/lib.rs:23-29`
- উপসর্গ: শুধু `skip_verify: true` কনফিগ করলেই TLS «সক্রিয়» ধরা হয় এবং সার্টিফিকেট যাচাই হয় না, নীরবে যাচাই বন্ধ হয়ে যায়।
- পরামর্শ: skip_verify ও ca_cert-এর মধ্যে পারস্পরিক বর্জন যাচাই করুন, অথবা স্পষ্ট দ্বিগুণ নিশ্চিতকরণ প্রয়োজন করুন।

### CVE পুনঃপরীক্ষা (নতুন আবিষ্কার, গুরুতরতা অনুযায়ী)

1. **[মাঝারি] rustls-webpki 0.102.8 ডিপেন্ডেন্সি ট্রিতে অবশিষ্ট** (RUSTSEC-2026-0049/0098/0099/0104: CRL distributionPoint বাইপাস, URI/wildcard name-constraints, মেরামত সংস্করণ 0.103.10)। মূল চেইন 0.103.13 (rustls 0.23.43 হয়ে, নিরাপদ); 0.102.8 async-nats 0.38.0 / rumqttc 0.25.1 হয়ে প্রবেশ করে, NATS/MQTT TLS ক্লায়েন্ট চেইন কভার করে। আপস্ট্রিম rustls 0.23-এ মাইগ্রেট করেনি, কোনো মেরামত সংস্করণ নেই — নিয়ন্ত্রিত ঝুঁকি, মন্তব্যসহ ট্র্যাক করার পরামর্শ।
2. **[মাঝারি-কম] rdkafka 0.36.2-এ এমবেডেড librdkafka cJSON 1.7.14 বহন করে** (CVE-2023-53154 ও cJSON সিরিজ; CVE-2025-57052 CVSS 9.8 চিহ্নিত কিন্তু প্রভাবিত ফাইল cJSON_utils.c librdkafka ব্যবহার করে না, প্রযোজ্যতা সন্দেহজনক)। আপস্ট্রিম মেরামত librdkafka 2.10+-এ (2026-03 PR #5346)। ecat-mq-kafka স্ট্যাটিক লিংক করে, librdkafka-sys প্যাকেজ সংস্করণ যাচাই করে আপগ্রেড ট্র্যাক করতে হবে।
