### নিরাপত্তা-সম্পর্কিত

#### 1. [গুরুতর] XOR «এনক্রিপশন» আসল এনক্রিপশন নয়
**ফাইল:** `ecat-config/src/encrypted.rs:45-56`
**সমস্যা:** `decrypt()` XOR + পুনরাবৃত্তি হওয়া কী ব্যবহার করে, এটি এনক্রিপশন নয় বরং অবফাসকেশন, সহজেই ভাঙা যায়। প্রতিটি বাইট অবস্থানে কী পুনরায় ব্যবহৃত হয়, ফলে সাইফারটেক্সট ফ্রিকোয়েন্সি অ্যানালাইসিসের জন্য অত্যন্ত ঝুঁকিপূর্ণ।
**পরামর্শ:** AES-256-GCM (`aes-gcm` crate) দিয়ে প্রতিস্থাপন করুন, অথবা স্পষ্টভাবে «অবফাসকেশন» হিসেবে চিহ্নিত করুন, «এনক্রিপশন» নয়।

#### 2. [গুরুতর] `execute_with`/`query_with` ডিফল্ট ইমপ্লিমেন্টেশন নীরবে প্যারামিটার ফেলে দেয়
**ফাইল:** `ecat-data/src/rdbms.rs:86-103`
**সমস্যা:** trait-এর ডিফল্ট ইমপ্লিমেন্টেশন প্যারামিটার গ্রহণ করে কিন্তু উপেক্ষা করে (`let _ = params;`), সরাসরি মূল `execute(sql)` কল করে। `ecat-data-sqlx` ছাড়া সব ব্যাকএন্ড (ClickHouse, QuestDB) এই আচরণ উত্তরাধিকার সূত্রে পায়। ব্যবহারকারী প্যারামিটারাইজড মেথড দিয়ে ব্যাকএন্ড প্রতিস্থাপন করলে প্যারামিটার নীরবে ফেলে দেওয়া হয়, ফলে SQL injection দুর্বলতা তৈরি হয়।
**পরামর্শ:** ডিফল্ট ইমপ্লিমেন্টেশনের «সাপোর্ট করা হয়নি» এরর ফেরত দেওয়া উচিত, অথবা প্রতিটি ব্যাকএন্ডে প্যারামিটার বাইন্ডিং সঠিকভাবে বাস্তবায়ন করা উচিত।

#### 3. [উচ্চ-ঝুঁকি] পাসওয়ার্ড URL-এ প্লেইনটেক্সটে এমবেড করা
**ফাইল:** `ecat-data-sqlx/src/lib.rs:40`, `ecat-data-redis/src/lib.rs:43`
**সমস্যা:** `connect_with_auth()` `replacen("://", "://user:pass@")` ব্যবহার করে ক্রেডেনশিয়াল সরাসরি URL-এ এমবেড করে। এই URL লগ, এরর মেসেজ বা ডিবাগ আউটপুটে রেকর্ড হতে পারে।
**পরামর্শ:** প্রতিটি ব্যাকএন্ডের নেটিভ অথেনটিকেশন মেকানিজম ব্যবহার করুন; অথবা অন্তত জোড়া দেওয়ার আগে ইউজারনেম/পাসওয়ার্ড URL-এনকোড করুন।

#### 4. [মাঝারি-ঝুঁকি] TLS কনফিগ ব্যর্থ হলে panic
**ফাইল:** 8টি data-* crate (ClickHouse, QuestDB, Elasticsearch, OpenSearch, ArangoDB, Neo4j, NebulaGraph, InfluxDB, IoTDB)
**প্যাটার্ন:** `.expect("TLS client build failed")` — সব `from_config()` কনস্ট্রাক্টর TLS কনফিগ ভুল হলে panic করে।
**পরামর্শ:** `from_config()`-কে `Result` ফেরত দেওয়ার জন্য পরিবর্তন করুন, অথবা TLS ক্লায়েন্ট নির্মাণ লেজি/ফল্ট-টলারেন্ট করুন।

### ফিচার সঠিকতা

#### 5. [উচ্চ-ঝুঁকি] `ecat-versioning` Header রাউটিং অকার্যকর
**ফাইল:** `ecat-versioning/src/lib.rs:56-64`
**সমস্যা:** `build_header_router()` সব সংস্করণ একই `/api` পাথের নিচে নেস্ট করে, কিন্তু সংস্করণ header অনুযায়ী ফিল্টার করে না। axum সব সংস্করণ রাউট একই পাথে নিবন্ধন করবে, ফলে রাউট কনফ্লিক্ট এবং অনির্ধারিত আচরণ হবে। `extract_version()` ফাংশন আছে কিন্তু কখনো রাউটিংয়ে ব্যবহার হয় না।
**পরামর্শ:** সব সংস্করণ একই পাথে সমতল করার বদলে axum middleware/layer ব্যবহার করে Accept header পরীক্ষা করে সঠিক সংস্করণ রাউটে পাঠান।

#### 6. [মাঝারি-ঝুঁকি] Redis TTL ট্রাঙ্কেশন: সাব-সেকেন্ড মেয়াদোত্তীর্ণ চিরকালের জন্য অ-মেয়াদোত্তীর্ণ হয়
**ফাইল:** `ecat-data-redis/src/lib.rs:76-77`
**সমস্যা:** `Duration::as_secs()` শূন্যের দিকে ট্রাঙ্কেট করে। 500ms TTL সেট করলে `secs == 0` হলে নীরবে চিরকালের জন্য অ-মেয়াদোত্তীর্ণ হয়ে যায়, `SET` পথে যায় `SETEX` নয়।
**পরামর্শ:** সাব-সেকেন্ড TTL-এর জন্য অন্তত 1 সেকেন্ড সেট করুন, অথবা `SETEX`-এর বদলে `SET ... PX` (মিলিসেকেন্ড) ব্যবহার করুন।

#### 7. [মাঝারি-ঝুঁকি] `StaticResolver::add_service` লক কনটেনশনে panic করে
**ফাইল:** `ecat-client/src/lib.rs:27-29`
**সমস্যা:** `try_write()` + expect ব্যবহার করে, অন্য কোনো লেখা লক ধারক থাকলে panic করবে। builder প্যাটার্ন এটিকে ট্রিগার করা কঠিন করে, কিন্তু কনকারেন্ট কোডে এটি টাইম বোমা।
**পরামর্শ:** `blocking_write()` ব্যবহার করুন (যদি সিঙ্ক্রোনাস কনটেক্সটে থাকেন) অথবা `&mut self` গ্রহণ করার জন্য পরিবর্তন করুন যাতে লকের প্রয়োজন এড়ানো যায়।

### কোড কোয়ালিটি

#### 8. [মাঝারি-ঝুঁকি] async কনটেক্সটে `std::sync::Mutex` ব্যবহার
**ফাইল:** `ecat-data-memcached/src/lib.rs:7,24`
**সমস্যা:** async trait ইমপ্লিমেন্টেশনে `std::sync::Mutex` ব্যবহৃত। লক ধারণের সময় অত্যন্ত সংক্ষিপ্ত হলেও (শুধু HashMap অপারেশন), উচ্চ কনটেনশনে তাত্ত্বিকভাবে async রানটাইম ব্লক করতে পারে।
**পরামর্শ:** এই মেমরি ক্যাশের নির্দিষ্ট ব্যবহারের ক্ষেত্রে, ক্রিটিক্যাল সেকশন অত্যন্ত সংক্ষিপ্ত এবং কোনো `.await` পয়েন্ট নেই বলে `std::sync::Mutex` ব্যবহার আসলে গ্রহণযোগ্য। কিন্তু ভবিষ্যতে লকের ভিতরে I/O অপারেশন করতে হলে `tokio::sync::Mutex` ব্যবহার করা উচিত।

#### 9. [কম] হাতে লেখা base64 ইমপ্লিমেন্টেশন
**ফাইল:** `ecat-registry-etcd/src/lib.rs:148-193`
**সমস্যা:** ~45 লাইনের হাতে লেখা base64 কোডেক, এতে বাউন্ডারি কেস বাগ থাকতে পারে। Rust ইকোসিস্টেমে `base64` crate-এর মতো পর্যাপ্ত রিভিউ করা বিকল্প আছে।
**পরামর্শ:** `base64` crate দিয়ে প্রতিস্থাপন করুন, রক্ষণাবেক্ষণের বোঝা এবং সম্ভাব্য বাগ কমান।

#### 10. [কম] `RandomBalancer` এলোমেলো নয়
**ফাইল:** `ecat-client/src/lib.rs:91-105`
**সমস্যা:** র্যান্ডম উৎস হিসেবে `Instant::now()` হ্যাশ ব্যবহার করে। একই ইনস্ট্যান্সের ভিতরে একই সময়ে করা কলগুলো একই «এলোমেলো» নির্বাচন পাবে। `checked_add(0)` একটি অপ্রয়োজনীয় অপারেশন।
**পরামর্শ:** `rand` crate ব্যবহার করুন বা অন্তত `std::collections::hash_map::RandomState` ব্যবহার করুন।

#### 11. [কম] `ecat-data-sqlx`-এ অপ্রয়োজনীয় `Arc<Vec<String>>`
**ফাইল:** `ecat-data-sqlx/src/lib.rs:79-87, 197-203`
**সমস্যা:** কলামের নাম `Arc<Vec<String>>`-এ মোড়ানো, কিন্তু প্রতিটি `Row` কনস্ট্রাক্টর পুরো কলাম নামের তালিকা ক্লোন করে (`(*cols).clone()`)। `Arc` শুধুমাত্র ইটারেশনের সময় একবার ব্যবহৃত হয়, `Rc` বা সরাসরি `clone()` যথেষ্ট।
**পরামর্শ:** `query()` এবং `query_with()`-এ `Arc<Vec<String>>`-কে সাধারণ `Vec<String>` দিয়ে প্রতিস্থাপন করুন। প্রতিটি সারির আলাদা ক্লোন খরচ Arc ডিরেফারেন্স + ক্লোনের সমান।

### ডিজাইন/আর্কিটেকচার

#### 12. [তথ্য] QuestDB GET + কুয়েরি প্যারামিটার ব্যবহার করে
**ফাইল:** `ecat-data-questdb/src/lib.rs:76, 91`
**সমস্যা:** SQL GET কুয়েরি প্যারামিটারের মাধ্যমে পাঠানো হয়, URL দৈর্ঘ্যের সীমাবদ্ধতা (সাধারণত ~2000-8000 অক্ষর) রয়েছে। বড় কুয়েরি ট্রাঙ্কেট হবে।
**পরামর্শ:** POST + body পদ্ধতিতে পরিবর্তন করুন, অথবা সহজ কুয়েরির জন্য GET রাখুন, জটিল কুয়েরিতে POST ব্যবহার করুন।

#### 13. [তথ্য] `#[allow(dead_code)]` চারপাশে ছড়িয়ে ছিটিয়ে
**ফাইল:** `ecat-registry-consul/src/lib.rs:225`, `ecat-data-memcached/src/lib.rs:25-28`, `ecat-auth/src/lib.rs:52`
**সমস্যা:** username/password ফিল্ড মেমরিতে সংরক্ষিত কিন্তু dead_code হিসেবে চিহ্নিত (in-memory memcached-এ প্রয়োজন নেই; auth-এর RSA ভেরিয়েন্ট এখনও বাস্তবায়িত নয়)।
**পরামর্শ:** অনুপস্থিত ফিচার পাথ বাস্তবায়ন করুন, অথবা এই ফিল্ডগুলো মুছুন, অথবা কেন রাখা হয়েছে তা ব্যাখ্যা করে ডকুমেন্টেশন যোগ করুন।

#### 14. [তথ্য] কিছু HTTP ক্লায়েন্টে Content-Type header নেই
**ফাইল:** `ecat-data-influxdb/src/lib.rs:96-103`, `ecat-data-clickhouse/src/lib.rs:87-89`
**সমস্যা:** কিছু POST রিকোয়েস্টে `Content-Type` header সেট করা নেই, সার্ভার-সাইড অটো-ডিটেকশনের উপর নির্ভর করে।
**পরামর্শ:** কম্প্যাটিবিলিটি নিশ্চিত করতে সবসময় স্পষ্ট Content-Type সেট করুন।

#### 15. [তথ্য] `ecat-auth` 500 লাইনের বেশি

## সিদ্ধান্ত

কোডবেস ভালো অবস্থায় আছে — কম্পাইল, টেস্ট এবং clippy সব পাস, কোনো unsafe কোড নেই, কোনো panic ম্যাক্রো নেই। সবচেয়ে গুরুত্বপূর্ণ দুটি সমস্যা হল **XOR «এনক্রিপশন»** (নিরাপত্তা মিথ্যা) এবং **প্যারামিটারাইজড কুয়েরির ডিফল্ট ইমপ্লিমেন্টেশন নীরবে প্যারামিটার ফেলে দেওয়া** (নিরাপত্তা দুর্বলতা)। Header রাউটিং ফিচারটিও সম্পূর্ণ অকার্যকর। অন্যান্য সমস্যা তুলনামূলকভাবে ছোট, রক্ষণাবেক্ষণযোগ্যতা স্তরের অপটিমাইজেশন।

**প্রস্তাবিত মেরামতের অগ্রাধিকার:**
1. `execute_with`/`query_with` ডিফল্ট ইমপ্লিমেন্টেশন → নীরবে প্যারামিটার ফেলে দেওয়ার বদলে এরর ফেরত দিন
2. XOR এনক্রিপশন → প্রকৃত AEAD এনক্রিপশন, অথবা «অবফাসকেশন» নামকরণ
3. Header সংস্করণ রাউটিং → প্রকৃত header রাউটিং বাস্তবায়ন
4. `from_config()` → expect-panic-এর বদলে Result ফেরত দিন
5. Redis TTL ট্রাঙ্কেশন → সাব-সেকেন্ড TTL-এ অন্তত 1 সেকেন্ড ব্যবহার করুন
